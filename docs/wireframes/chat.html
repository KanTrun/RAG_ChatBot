How does the ingestion pipeline work?

How does the document ingestion pipeline work? I want to understand the full flow from upload to searchable chunks.

The document ingestion pipeline follows a multi-stage async process:

  1. Upload & Storage -- The raw document (PDF, DOCX, etc.) is uploaded via the API and stored in the file storage system (local FS in dev, S3/MinIO in prod). architecture.pdf, p.12
  2. Parsing -- PyMuPDF extracts text content. For complex or scanned documents, Marker is used as fallback with OCR capabilities.
  3. Chunking -- LlamaIndex node parsers split the document into semantic chunks with configurable size (default: 512 tokens) and overlap (64 tokens). chunking-guide.pdf, p.5
  4. Embedding -- BGE-M3 generates dense + sparse embeddings for each chunk. This enables hybrid search (vector similarity + BM25).
  5. Storage -- Embeddings and chunk metadata are stored in PostgreSQL with pgvector (HNSW index) and tsvector for full-text search. db-schema.pdf, p.3

The entire process runs asynchronously via Celery + Redis, so users aren't blocked while large documents are being processed.
